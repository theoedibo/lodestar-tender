# Lodestar Tender — Database Design

The schema lives at `prisma/schema.prisma` and is the source of truth; this document explains the design decisions behind it. All tables use `gen_random_uuid()` UUID primary keys and snake_case column/table names in Postgres (Prisma models use camelCase and `@@map`/`@map`).

## 1. Entity Groups

```
Identity/Tenant     organizations, users, organization_members
Company             company_profiles, company_services, company_products,
                     company_certifications, company_projects, company_personnel,
                     company_equipment, company_financials, company_legal_records
Documents            documents, document_extractions, document_evidence, document_reviews
Tender Sources       tender_sources, source_runs, source_items
Tenders              tenders, tender_documents, tender_requirements,
                     tender_evaluation_criteria
Qualification        qualification_assessments, qualification_results,
                     qualification_gaps, qualification_evidence
Bids                 bid_workspaces, bid_tasks, bid_deadlines
AI / Operations      agent_runs, agent_events, notifications
Platform Admin       admin_actions, admin_org_notes
Scouting             scouting_profiles, scouting_bdm_recipients,
                     org_source_subscriptions, scouting_matches
Bid packs            bid_packs
Dispatch             bid_pack_dispatches
Billing              organizations.plan_tier/.billing_status/… (no new table), billing_events
```

This matches `PROJECT_SPEC.md`'s scope: every table here backs a V1 feature or its immediate scaffolding (Bids). No table was added speculatively beyond what the domain model in the product brief requires.

## 2. Tenancy Strategy

Two clearly separated categories:

- **Organization-owned** (Company, Documents, Qualification, Bids, and `agent_runs`/`notifications`): every table carries a denormalized `organization_id`, even on child tables reachable through a parent (e.g. `company_certifications.organization_id`, not just `company_profile_id` → `company_profiles.organization_id`). This is deliberate: Row Level Security policies stay single-table (`organization_id = current_organization_id()`) instead of needing a join through every parent, which is both simpler to audit and faster.
- **Platform-shared** (Tender Sources, Tenders): no `organization_id` at all. A tender discovered from a source is a fact about the world, not about any one tenant — many organizations may view and qualify against the same tender. Tenancy begins at `qualification_assessments`, which is where an organization's own interpretation of a tender is recorded.

Row Level Security (enabled per table in a Supabase SQL migration, not generated by Prisma) follows this pattern for every organization-owned table:

```sql
alter table company_profiles enable row level security;

create policy "org_isolation_select" on company_profiles
  for select using (
    organization_id in (
      select organization_id from organization_members
      where user_id = auth.uid()
    )
  );
-- equivalent policies for insert/update/delete, plus role checks
-- (e.g. only OWNER/ADMIN may delete) added where the action warrants it.
```

Platform-shared tables (`tenders`, `tender_sources`, ...) get a simpler policy: readable by any authenticated user, writable only by the service role (ingestion jobs).

## 3. Identity / Tenant

| Table | Key columns | Notes |
|---|---|---|
| `organizations` | `id` PK | The tenant boundary. |
| `users` | `id` PK (= Supabase `auth.users.id`) | Mirrors Supabase Auth; no credentials stored here. |
| `organization_members` | `id` PK, `(organization_id, user_id)` unique, FK → `organizations`, `users` | `role` enum `OrganizationRole` (`OWNER`, `ADMIN`, `MEMBER`, `VIEWER`) drives both RLS and in-app authorization checks. |

## 4. Company (Capability Passport)

`company_profiles` is 1:1 with `organizations` (`organization_id` unique). All child tables (`company_services`, `company_products`, `company_certifications`, `company_projects`, `company_personnel`, `company_equipment`, `company_financials`, `company_legal_records`) FK to `company_profiles.id` with `onDelete: Cascade`, and each carries `organization_id` directly per the tenancy strategy above.

Design choices:

- **`company_legal_records` is intentionally generic** (`record_type: string`, not an enum, not fixed columns per document type). This is the table that would otherwise be tempted to hard-code CAC/FIRS/PENCOM-style fields — it does not. See `PROJECT_SPEC.md` §"Non-goals".
- **`company_financials` is one row per financial year**, not a single mutable record — a company's turnover history matters for multi-year requirements and for showing trend, not just the latest figure.
- Money is always an `(amount: Decimal(18,2), currency: Char(3))` pair, never a bare number — see `contract_value_*`, `annual_turnover_*`, `bonding_capacity_*`, `estimated_value_*` on `tenders`.
- Confidence/probability values are `Decimal(4,3)` (0.000–1.000); score/percentage values are `Decimal(5,2)` (0.00–100.00). Kept as `Decimal`, not `float`, so comparisons in the qualification engine are exact.

## 5. Documents — Evidence Model

| Table | Purpose |
|---|---|
| `documents` | Organization-owned uploaded evidence file. Original file path (`storage_path`) is never overwritten. |
| `document_extractions` | One row per AI extraction pass over a document: `document_type` (free text), `extracted_text`, `structured_data` (JSON), `confidence`, `source_page`. |
| `document_evidence` | Links a document (and optionally one specific extraction) to the company-capability record it supports. |
| `document_reviews` | Human correction/verification trail: `reviewed_by_user_id`, `corrections` (JSON), `notes`. |

**Polymorphic evidence reference.** `document_evidence.capability_type` (e.g. `"company_certification"`, `"company_project"`) plus `capability_record_id` (a UUID) identify the target row in whichever `company_*` table the evidence supports. Postgres cannot FK-constrain a column against a table chosen at runtime, so this reference is **enforced at the application layer**, not the database. This is a deliberate, scoped exception to "always use a real FK" — the alternative (a nullable FK column per capability type on `document_evidence`) would require a schema migration every time a new capability type is added, which conflicts with the requirement that companies have flexible, heterogeneous evidence. The same trade-off applies to `qualification_evidence.capability_record_id` (§7). Application code that writes either table must validate `capability_type` against a known allow-list and verify the referenced row exists and belongs to the same organization before insert.

## 6. Tender Sources & Tenders (platform-shared)

| Table | Purpose |
|---|---|
| `tender_sources` | One row per connector (`source_key` unique slug), e.g. `nipex`, `ungm`. |
| `source_runs` | One ingestion run per source invocation; `status`, counts, error. |
| `source_items` | Raw payload as fetched, kept for audit regardless of whether it produced a new `tender`. Not unique-constrained — the same external item is expected to reappear across runs. |
| `tenders` | Normalized tender. `(source_id, source_identifier)` unique — this is the deduplication key (see `SOURCE_CONNECTOR_ARCHITECTURE.md`). |
| `tender_documents` | Notice/spec/addendum files fetched from the source. **Separate from `documents`** — these are platform-shared, not organization-owned. |
| `tender_requirements` | Extracted requirement; `category` enum `RequirementCategory` (18 values, see §8), `requirement_type` free text within the category, `mandatory`, `confidence`, optional `source_document_id`/`source_page` for traceability back to `tender_documents`. |
| `tender_evaluation_criteria` | Extracted scoring criteria, optional `weight`. |

`tenders.foreign_bidder_policy` (enum `ForeignBidderPolicy`: `OPEN_TO_FOREIGN`, `LOCAL_PARTNER_REQUIRED`, `LOCAL_REGISTRATION_REQUIRED`, `RESTRICTED`, `UNKNOWN`) and `local_partner_required` are structured fields specifically so the qualification engine can evaluate eligibility deterministically rather than re-reading free text every time.

## 7. Qualification

| Table | Purpose |
|---|---|
| `qualification_assessments` | One per (organization, tender) qualification run. `match_score` and `confidence` are `Decimal(5,2)`, computed by deterministic logic (see `AI_ARCHITECTURE.md`) — never written directly from an LLM response. `recommendation` enum `Recommendation` (`PURSUE`, `REVIEW`, `PARTNERSHIP_REQUIRED`, `DO_NOT_PURSUE`). |
| `qualification_results` | One per requirement per assessment. `outcome` enum `RequirementOutcome` (`SATISFIED`, `NOT_SATISFIED`, `UNKNOWN`, `NEEDS_REVIEW`, `NOT_APPLICABLE`, `ELIGIBILITY_BLOCKER`, `PARTNERSHIP_REQUIRED`). `explanation` is always populated — see `AI_ARCHITECTURE.md` §"Explainability". |
| `qualification_evidence` | Explainability link from a result to the specific company-capability record (and, optionally, the uploaded `documents` row) that justified the outcome. Same polymorphic-reference caveat as `document_evidence` (§5). `evidence_status` enum `EvidenceStatus` (`VERIFIED`, `LIKELY`, `UNKNOWN`, `NOT_SATISFIED`) — kept distinct from `qualification_results.outcome` because one result can be supported by multiple evidence rows of varying strength. |
| `qualification_gaps` | Materialized, human-readable gap for a `NOT_SATISFIED`/`ELIGIBILITY_BLOCKER` result — e.g. "Tender requires $20M, company evidence shows $7.2M, gap $12.8M" — so the UI never has to recompute the gap narrative. |

`qualification_assessments.tender_id` and `bid_workspaces.tender_id` use `onDelete: Restrict` (not `Cascade`) — a tender with existing tenant assessments or bid workspaces should not be silently deletable; the platform-side data lifecycle should archive/deactivate tenders instead of deleting them once any organization has acted on them.

| `RequirementOutcome` | `SATISFIED`, `NOT_SATISFIED`, `UNKNOWN`, `NEEDS_REVIEW`, `NOT_APPLICABLE`, `ELIGIBILITY_BLOCKER`, `PARTNERSHIP_REQUIRED` |
| `EvidenceStatus` | `VERIFIED`, `LIKELY`, `UNKNOWN`, `NOT_SATISFIED` |
| `Recommendation` | `PURSUE`, `REVIEW`, `PARTNERSHIP_REQUIRED`, `DO_NOT_PURSUE` |

| `AgentRunStatus` | `RUNNING`, `SUCCEEDED`, `FAILED` |

`RequirementCategory` classifies the *kind* of requirement only — never its jurisdiction-specific content. No enum in this schema encodes a country-specific document or registration name; those live as free-text values (`requirement_type`, `company_legal_records.record_type`, etc.) precisely so no code path special-cases a country. See `PROJECT_SPEC.md` §"Non-goals".

## 9. Indexes

Beyond primary keys and the FK columns Postgres auto-indexes:

- Every organization-owned table: `@@index([organizationId])` — the dominant query pattern is "everything for this tenant".
- `tenders`: `@@unique([sourceId, sourceIdentifier])` (dedup key), `@@index([country])`, `@@index([deadline])` — supports source ingestion upserts and the two most common tender-list filters.
- `tender_requirements`: `@@index([tenderId])`, `@@index([category])`.
- `document_evidence` / `qualification_evidence`: indexed on the polymorphic pair `(capability_type, capability_record_id)` and on their owning document/result, to support both "what evidence supports this capability" and "what evidence backs this result" lookups.
- `qualification_assessments`: `@@index([organizationId])`, `@@index([tenderId])` — supports both "this org's assessments" and "who has assessed this tender" queries.

No additional indexes were added speculatively; more will be added once real query patterns emerge from the application (`ARCHITECTURE.md` §"Future Scaling").

## 10. Bids & AI/Operations (design-only in Phase 0)

`bid_workspaces` (unique per `(organization_id, tender_id)`), `bid_tasks`, `bid_deadlines` mirror `PROJECT_SPEC.md` §"Bid Workspace" — implemented starting `IMPLEMENTATION_PLAN.md` Phase 7.

`bid_workspaces` gained eight nullable columns in Phase 15 (`supabase/migrations` unaffected — RLS is row-level, already covers the table): `submitted_at`, `submitted_via` (`"BID_ROOM"` \| `"MANUAL"`, free string like `notifications.type`), `submitted_by_email`, `submission_reference`, `receipt_storage_path`/`receipt_file_name`, `not_submitted_at`, `not_submitted_reason`. Written only by `backend/lib/bid-workspace.ts`'s `markSubmitted()`/`markNotSubmitted()` — called from the no-login bid room (`backend/actions/bid-room.ts`) or, in principle, a future authenticated path. A later `markSubmitted` clears a prior not-submitted state rather than leaving stale fields.

`agent_runs`/`agent_events` log every AI module invocation (module name, status, timing, structured event payloads) for debugging and cost/latency observability; `organization_id` is nullable because some runs (e.g. processing a platform-shared tender document before any org has qualified against it) aren't organization-scoped. `notifications` is intentionally minimal (`type`, `message`, `read_at`) — its delivery mechanism (email, in-app, etc.) is a future-phase concern, not a schema concern.

## 11. Platform Administration (added post-Phase 6)

| Table | Purpose |
|---|---|
| `admin_actions` | Audit trail: one row per action a platform admin takes (`REQUALIFY`, `SUSPEND_ORG`, `REACTIVATE_ORG`, `ADD_NOTE`, `RESEED_DEMO`, …). `organization_id` nullable for platform-wide actions. Also feeds the admin activity feed. |
| `admin_org_notes` | Free-text internal notes an admin keeps about an organization; visible only in the `/admin` console. |
| `organizations.suspended_at` | Nullable. Set by an admin to suspend an organization — its members are then blocked at `requireOrganizationContext()` (→ `/suspended`). |

`admin_actions` and `admin_org_notes` are **not organization-owned in the RLS sense**: RLS is enabled with no `authenticated` policy, so they are reachable only through the Prisma owner / service-role connection — same pattern as `source_runs`. Platform-admin identity is an env allow-list (`PLATFORM_ADMIN_EMAILS`), never a database role, never self-service. See `ARCHITECTURE.md` §8 "Platform-admin exception".

## 12. Scouting configuration (added Phase 11)

| Table | Purpose |
|---|---|
| `scouting_profiles` | One per organization (`organization_id` unique). The per-client policy for the autonomous loop: `active`, `autonomy_level` (`AUTO` \| `REVIEW_FIRST`), `countries[]` / `keywords[]` / `min_value_amount` / `max_value_amount` / `value_currency` filters, `min_response_days`. Read by the Phase 12 fan-out and the `/settings/scouting` match preview. |
| `scouting_bdm_recipients` | The BD managers a finished submission pack is emailed to (Phase 14). `{organization_id, email, name?}`; dedupe on `(organization_id, email)` is enforced in code, not the schema. |
| `org_source_subscriptions` | Which sources an organization scouts. `@@unique([organization_id, source_id])`, `status` (`ACTIVE` \| `PAUSED` \| `PENDING_ONBOARDING` \| `ERROR`), `inbound_address?` (vendor-portal email, Phase 9b), `credential_ref?` (Phase 11b vault), `onboarding_notes?`. Every free connector is auto-subscribed `ACTIVE` for every org (on org creation and on the cron tick's `backfillFreeSubscriptions`). |
| `scouting_matches` (Phase 12) | One row per (organization, tender) the autonomous fan-out considered. `@@unique([organization_id, tender_id])`, `@@index([organization_id, status])`. `status` (`QUALIFYING` \| `QUEUED` \| `APPROVED` \| `DISPATCHED` \| `DISMISSED` \| `SKIPPED` \| `ERROR`), `decision` (`AUTO_DISPATCH` \| `REVIEW` \| `SKIP`, nullable), `decision_reasons String[]`, `assessment_id?` (→ `qualification_assessments`, `onDelete: SetNull`), `recommendation?`, `match_score?`, `confidence?`, `reviewed_by_id?` (bare `users.id` scalar, as `document_reviews`), `reviewed_at?`, `dispatched_at?`, `error?`. The review queue is `status = QUEUED`; a person's decision (APPROVED / DISMISSED) is never overwritten by a later fan-out. |

All four are organization-owned and get the uniform `is_organization_member(organization_id)` RLS policy (`supabase/migrations/20260910175500_scouting_rls.sql`, `20260910194300_scouting_fanout_rls.sql`).

## 13. Bid packs (Phase 13)

| Table | Purpose |
|---|---|
| `bid_packs` | The assembled submission ZIP for a qualified, pursue-worthy opportunity — `status` (`CURRENT` \| `SUPERSEDED`), `storage_path` (private bucket, `<org>/bid-packs/…`), `file_name`, `size_bytes`, `file_count`, `manifest Json` (the embedded `manifest.json`: which file backs which requirement), `assessment_id` (→ `qualification_assessments`), `scouting_match_id?`. `@@index([organization_id])`, `@@index([tender_id])`. Re-assembly keeps the prior row, flipped to `SUPERSEDED`. |

Organization-owned, uniform member RLS (`supabase/migrations/20260910213330_bid_packs_rls.sql`). The ZIP bytes never leave the private bucket except through a click-time signed URL minted by the server layer.

## 14. BDM dispatch (Phase 14)

| Table | Purpose |
|---|---|
| `bid_pack_dispatches` | One row per (bid pack, recipient) send attempt — `status` (`QUEUED`/`SENT`/`DELIVERED`/`BOUNCED`/`FAILED`), `provider` (`resend`), `provider_message_id`, `bid_room_expires_at` (the magic link's own expiry, checked independently of the token's claimed expiry), `sent_at`/`delivered_at`/`bounced_at`, `error_message`. `@@index([organization_id])`, `@@index([bid_pack_id])`. |

Organization-owned, uniform member RLS (`supabase/migrations/20260911094000_bid_pack_dispatches_rls.sql`). The bid-room magic link itself is not a database row — it's a stateless, HMAC-signed token (`backend/domain/dispatch/magic-link.ts`) embedding the dispatch id and an expiry; nothing about it is stored or needs to be looked up to verify the signature, only to load the content once verified.

## 15. RLS audit + rate limiting (Phase 16)

**RLS audit** — queried the live database's `pg_tables`/`pg_policies` directly
(not just the migration files, which could in principle drift from what was
actually applied) for every one of the 40 application tables. Result: every
table has RLS enabled; every organization-owned table carries the uniform
`org_members_full_access` policy; `tender_sources`/`tenders`/
`tender_documents`/`tender_requirements`/`tender_evaluation_criteria` (platform-
shared) carry the `authenticated_can_select` policy; and exactly the four
tables meant to be service-role-only — `admin_actions`, `admin_org_notes`,
`source_runs`, `source_items` — have RLS enabled with **no** policy for
`authenticated`. No gaps.

**Rate limiting** — no new table. `backend/lib/rate-limit.ts` counts rows in a
recent window against tables that already exist for other reasons:
`agent_runs` (AI calls, 10/org/min), `bid_pack_dispatches` (20/org/hour),
`bid_packs` (10/org/min). `processUploadedDocument` previously wrote no
`agent_runs` row at all despite §10's claim that it logs every AI invocation —
fixed in the same pass, which is also what makes it rate-limitable.

## 16. Billing (Phase 17; payment amounts added Phase 19)

| Table / columns | Purpose |
|---|---|
| `organizations.plan_tier` / `.billing_status` / `.trial_ends_at` / `.billing_provider` / `.billing_customer_id` / `.billing_subscription_id` / `.current_period_end` | The mirror of a provider's subscription state. `trial_ends_at` **defaults at the database level** to `now() + 14 days` (`@default(dbgenerated(...))`, not just app-code default) — every org, however created, starts with a real trial rather than reading as already-expired the moment `backend/lib/billing.ts`'s gate checks it. |
| `billing_events` | Every webhook event received from a billing provider — an audit trail independent of whether it changed anything. `organization_id` nullable (an event the org-resolution logic couldn't place is still recorded, with `error_message` set). `@@unique([provider, external_id])` gives idempotency against provider redelivery. `amount_minor_units` / `currency` (migration `billing_payment_amounts`, both nullable) — set only when the provider's payload actually states a charge amount (a completed checkout, a paid invoice, a successful charge); null for pure status-transition events. This is what `/admin/billing` sums into "revenue this month," grouped by currency and never combined across them. |

Organization-owned, but **read-only** RLS for `billing_events`
(`supabase/migrations/20260911155200_billing_events_rls.sql`) — a member can
see their own org's billing history; only the Prisma owner connection (the
webhook routes) ever writes it. The billing columns on `organizations` need
no separate policy — RLS is row-level, and members already have full access
to their own organization row from the Phase 1 migration. `/admin/billing`
reads `billing_events` cross-organization via the platform-admin Prisma
connection (service-role, bypasses RLS — same as every other `/admin/*` page),
not through the member-scoped RLS policy above.
